📂 Path Traversal — When “../” Becomes a Skeleton Key

Path Traversal is that vulnerability where the server politely asks:

“Which file do you want?”

And you respond:

“Yes.”

In one line:
Path Traversal = Escaping the intended folder using ../ and reading files you were never supposed to see.

It’s like the application hands you a file browser and says:

“Promise me you’ll only open your own files 😇”
And you, as a hacker, obviously don’t.

🧠 The Basic Idea (In Easy Language)

The app wants to serve you, say, PDF reports from: 

/var/www/app/reports/

So it has a URL like:

/download?file=invoice_123.pdf

On the backend, some genius wrote:

file_path = "/var/www/app/reports/" + user_input
open(file_path)

Now if you give: 

invoice_123.pdf

Cool, legit. But if you give:

../../../../etc/passwd

Then the path becomes:

/var/www/app/reports/../../../../etc/passwd

The OS goes: “Yeah that’s valid, no problem.” And you just read a system file.

That’s Path Traversal.
You walk out of the “allowed” directory and start exploring the whole file system.

📍 Where Path Traversal Usually Appears

Any feature that deals with files or paths is suspicious by default:

  • /download?file=
  • /view?template=
  • /image?name=
  • /logs?file=
  • Backup restore / export functions
  • Custom theme/template loaders

If the request looks like: 

GET /something?file=report1.txt

…your brain should auto-complete it as:

GET /something?file=../../../../etc/passwd

🧪 Classic Payloads (Your Starter Pack)

Basic traversal to read Linux /etc/passwd:

../../../../etc/passwd

URL-encoded (because devs sometimes block ../):

..%2F..%2F..%2F..%2Fetc%2Fpasswd

Double-encoded (when they got “smart” and decode once):

..%252F..%252F..%252F..%252Fetc%252Fpasswd

On Windows systems, target:

..\..\..\..\windows\win.ini

You’re basically testing how much the server respects boundaries. Spoiler: usually not much.

🔍 Realistic Example — File Download Endpoint

Normal user request:

GET /download?file=invoice_2024_01.pdf

Server logic (very optimistic):

base = "/var/www/app/invoices/"
file = base + request.GET["file"]
return open(file)

You change:

/download?file=../../../../etc/passwd

If the server responds with something like:

root:x:0:0:root:/root:/bin/bash
daemon:x:1:1:daemon:/usr/sbin:/usr/sbin/nologin
...
🎉 You just performed a Path Traversal and read a sensitive system file. Welcome to “This is now a critical vulnerability” territory.

🔎 What to Try Reading (Carefully, In Authorized Environments)

On Linux targets:

  • /etc/passwd – basic sanity check
  • /etc/hostname
  • /etc/hosts
  • Application configs like: config.php, .env

On Windows targets:

  • C:\Windows\win.ini
  • C:\Windows\System32\drivers\etc\hosts

If you start hitting env/config files, you’re in “credentials-leaking” level impact.

🧬 Bypassing Filters (Because Devs Google “How to block ../”)

Common defenses you’ll see:

  • Blocking exact string ../
  • Replacing ../ with empty string
  • Restricting extensions (e.g., only .pdf)

Tricks to Try

  • Double encoding: %2e%2e%2f, %252e%252e%252f
  • Using ..\/ or mixed slashes
  • Adding junk like ....// which normalizes to ../
  • Appending valid extensions: ../../../../etc/passwd%00.pdf on older systems
Remember: Even if ../ is blocked, the path might still normalize back to a parent directory after the filesystem resolves it.

💣 Path Traversal → Source Code → Full Pwn

Path Traversal doesn’t stop at /etc/passwd. That’s just your “yes, it works” file.

You can aim for:

  • Application source code (e.g., index.php, controllers, routes)
  • Configuration files with DB credentials
  • API keys, tokens, mail credentials

Once you get: 

DB_PASSWORD="something-super-secure-but-actually-not"

…you’ve moved from “file read bug” to “database compromise”.

🔐 How Developers Should Fix It (In Theory)

But we both know if they did, you’d have fewer bounties. Anyway:

  • Use a strict allow-list of filenames or IDs instead of raw file paths.
  • Never trust user input as part of a filesystem path.
  • Normalize and validate the path server-side, and ensure it stays under the intended directory.
  • Use OS-level sandboxing / chroot where possible.
Golden Rule:
If the user can influence the path → you must assume they will try to escape it.

🕵️‍♂️ Quick Hacker Checklist for Path Traversal

  • Find any parameter that looks like it references a file: file=, path=, template=, log=, download=.
  • Try ../ once and see what happens.
  • If blocked, try encoded / double-encoded payloads.
  • First aim for /etc/passwd or win.ini to prove impact.
  • Then go after application configs / source code.

If you can read sensitive files that belong to the system or application, you’ve got yourself a solid, high-impact vulnerability.

🎯 Final Thoughts

Path Traversal is one of those vulnerabilities that is:

  • Simple to understand
  • Fun to test
  • Often underestimated by developers
  • Capable of turning into full system compromise

All you’re doing is saying:

“Hey server, show me this file.”
And the server says:
“Say no more.”

As always — use this knowledge only on authorized targets. You want bug bounty payouts, not court dates.
